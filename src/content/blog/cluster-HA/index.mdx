Si bien existen muchas formas de configurar un cluster de alta disponibilidad, en este artículo vamos a ver una forma de hacerlo usando **AlmaLinux**, **Pacemaker** y **Corosync**.

## Algunos conceptos de Clustering

Un clustering es un conjunto de computadoras que en el caso de un cluster de HA (High Availability) tienen el objetivo de que si una de las maquinas falla, otra del cluster pueda remplazarla y continuar con el servicio ofrecido.
En el caso de clustering de altas prestaciones (HPC) el objetivo es que varias maquinas puedan compartir el poder de computo entre si para poder resolver algun problema puntal, en este caso problemas que requieren mucho poder de computo.

Algunas ideas puntuales:
- **Tipos de Cluster**:
  - Alta Disponibilidad: conjunto de nodos donde uno de ellos toma el rol de primario y los demas de secundario. en caso de que el primario caiga alguno de los demas nodos tomara su lugar.
  - Balance Carga: conjunto de nodos donde todos los nodos son iguales y se reparten la carga entre ellos.
  - Altas Prestaciones: conjunto de nodos que comparten el poder de computo entre ellos para resolver problemas que requieren mucho poder de computo.
  - Almacenamiento: conjunto de nodos que comparten el almacenamiento entre ellos para poder ofrecer un almacenamiento distribuido y redundante.
- Virtual IP: los servicios ofrecidos por el cluster tendran que ser accedidos por una IP flotante, que es una IP que puede estar en cualquiera de los nodos del cluster. esto permite que si un nodo cae, otro nodo pueda tomar la IP y continuar ofreciendo el servicio.
- Almacenamiento Compartido:
  - NAS: Network Attached Storage, es un almacenamiento compartido que se ofrece a traves de la red. los nodos del cluster pueden acceder a este almacenamiento para compartir archivos entre ellos.
  - SAN: Storage Area Network, es un almacenamiento compartido que se ofrece a traves de una red de alta velocidad. los nodos del cluster pueden acceder a este almacenamiento para compartir archivos entre ellos.
  - DAS: Direct Attached Storage, es un almacenamiento compartido que se ofrece a traves de una conexion directa. los nodos del cluster pueden acceder a este almacenamiento para compartir archivos entre ellos.
- Heartbeat: es un servicio que permite a los nodos del cluster comunicarse entre ellos para saber si alguno de ellos esta caido o no. este servicio es ofrecido por corosync.
- Failover: es el proceso de migracion de los servicios de un nodo caido a otro node del cluster.
- Fancing: es el proceso de aislamiento de un nodo caido en el cluster.
- Cuorum: es el numero minimo de nodos que tienen que estar activos para que el cluster tome deciciones sobre por ejemplo dar de baja un nodo en particular. esto es para evitar falsos positivos en la caida de un servicio.
- STONITH: es un mecanimos de hardware que permite apagar un nodo del cluster, evidanto asi que aun asilado del cluster afecte por ejemplo a los discos compartidos o sature la red con mensajes de heartbeat.

## Nuestro objetivo

El objetivo de este laboratorio es configuara un cluster de HA usando dos maquinas virtuales. La idea es alojar un servidor web usando apache y replicando la informacion de la misma mediante DRBD.



## Instalacion de almalinux

Para esta prueba tenemos que tener dos maquinas virtuales corriendo almalinux en su ultima version (creo que van por la version 9.2).
Una ves instaldo podremos proceder con los siguientes pasos.

## Facing o STONITH 

Cuando uno de los nodos del cluster se cae, el otor nodo puede seguir funcionando y tomar el control de los recursos, pero si el nodo que se cayo sigue funcionando de alguna manera, puede generar problemas de integridad de datos. Para evitar esto, se utiliza STONITH (Shoot The Other Node In The Head), que básicamente es un mecanismo para asegurarse de que el nodo caído no pueda seguir interfiriendo con el clúster.
En muchos casos esto se implementa con hardware especializado , pero como este cluster esta montado en maquinas virtuales, por el momento deshabilitaremos este mecanismo.

#### Deshabilitamos el facing.

```bash
[root@fz1 user]# pcs property set stonith-enabled=false
[root@fz1 user]# pcs cluster verify --full
[root@fz1 user]#
```
> [!NOTE]
> Tenemos que deshabilitar el facing en un solo de los nodos por que esto afecta a todo el nodo.

```bash
[root@fz2 user]# pcs cluster verify --full
[root@fz2 user]#
```

## Creamos el clouster pasivo - activo

En nuestro caso vamos a montar un cluster pasivo - activo, esto significa que uno de los nodos estara activo y el otro estara en espera. Cuando el nodo activo falle, el nodo en espera tomara el control de los recursos.
Para la prueba montaremos una web con apache y DRBD para sincronizar los datos de la web.

Creamos el archivo de configuracion de DRBD, para nuestra web.


```bash
[root@fz# user]# cat <<END >/etc/drbd.d/wwwdata.res
resource "wwwdata" {
  device minor 1;
  meta-disk internal;

  net {
    protocol C;
    fencing dont-care;
    verify-alg sha1;
  }
  handlers {
    fence-peer "/usr/lib/drbd/crm-fence-peer.9.sh";
    unfence-peer "/usr/lib/drbd/crm-unfence-peer.9.sh";
  }
  on "fz1" {
    disk "/dev/drdb/drdb_fz";
    node-id 0;
  }
  on "fz2" {
    disk "/dev/drdb/drdb_fz";
    node-id 1;
  }
  connection {
    host "fz1" address 10.0.18.117:7789;
    host "fz2" address 10.0.18.118:7789;
  }
}
END
```

> [!IMPORTANT]
> La linea de facing dont-care es muy importante por que sino cuando probemos un failover el clouster no podra promocionar al otro nodo. al indicarle esto el nodo no esperar a que el mecanismo de facing apague el nodo caido, sino que promociona directamente el siguiente nodo.
